## 1. 背景与目标

网站目前是两大块（ZZZ + HSR），要扩为**三大块**：新增**货币战争**。同时确立以 **data/ 文件夹（md + 图片）为唯一权威资料层** 的数据管线：

```
各 wiki 站 ──爬虫──▶ data/（md + images）
                       │
                       ├──▶ ① 生成 diff 报告（新增/修改/删除，字段级）──▶ 用户确认 ✅
                       └──▶ ② 同步脚本 ──▶ MySQL（图片入库 LONGTEXT）──▶ 网站
```

- **非目标**：抽卡模拟器、强度榜/攻略观点类内容、地图数据（无可靠源）、直接引用 data/ 路径的前端展示。

## 3. 关键决策记录（AD）

| # | 决策 | 内容 |
|---|---|---|
| AD-1 | 资料文件夹名 | `HengBerGer/data/`，结构：`zzz/`、`hsr/`、`currency/{season1,season2}/`、`images/{zzz,hsr,currency}/` |
| AD-2 | 图片进网站方式 | **保持现状（入库 LONGTEXT）**；data/images 只是资料层，前端**不直接引用** data 路径 |

| AD-4 | git 策略 | data/ 的 **md 进 git**（可 diff/回滚），`data/images/` 加 .gitignore 忽略（体积） |
| AD-5 | 卡池范围 | 只要**历史卡池时间表**（up 角色/武器 + 起止日期），不含抽卡模拟 |
| AD-6 | 内鬼内容 | 与正式内容一视同仁，**全部展示、不打来源标记**（数据模型不设 source/leak 字段） |

| AD-8 | 主源策略 | 每类数据定一个主源，更新优先从主源抓；高频字段定期与其他站抽查对比（详见 docs/17 §5 草案，Phase 1 定稿） |

| AD-11 | 数据不进网站的例外 | nanoka-update skill 维护的两个镜像仓库流程与本项目脱钩 |

## 5. 阶段计划（Phase 0–5）

### Phase 0 — 资料层地基（data/ + 种子）
- 建 `data/` 目录结构（AD-1），每类实体配 `state.json`（数据版本、最后爬取时间、主源）
- 统一 md 规范：front-matter（id/name/来源/版本/更新时间）+ 表格正文（沿用 nanoka 风格）
- 从两个本地镜像迁移 19 类种子（AD-10）；`.gitignore` 加 `data/images/`（AD-4）
- **验收**：19 类种子就位，目录结构评审通过

### Phase 1 — 字段级深挖 + 主源定稿（UI 细化的输入）
- 19 类逐个：主源详情页字段清单 ∪ nanoka 种子字段 → **字段能力矩阵**
- 定稿每类 **md schema = DB 表结构 = 表单字段 = 详情页展示字段**（根治旧病：P1-7/BE-12 表单与数据错位）
- 时装并入角色的字段形态在此确定
- 补侦察：货币战争在 BWIKI/米游社/appfeng 有无栏目（找抽查对象）
- 图片源定主
- **产出**：字段矩阵文档 + 主源分配终稿；**验收**：19 类 schema 全确认

### Phase 2 — 爬虫（采集器）开发
- 每类实体一个采集器（米游社 API / BWIKI HTML / GameKee API / zzz.gg / SRS / appfeng / bittopup / nanoka 网站 …）
- 只写 `data/`；图片下到 `data/images/`
- **diff 报告 + 确认门禁（AD-3）作为硬性契约实现**
- 抽查机制：高频字段跨站对比，异常写入报告
- **验收**：一轮真实爬取，报告准确，未确认绝不产生同步动作

### Phase 3 — 同步层 + DB 改造
- `sync` 脚本：data/ → MySQL；图片读文件转 LONGTEXT 入库（AD-2）
- 新表：`zzz_enemies`、`zzz_gacha`、`hsr_enemies`、`hsr_gacha`、`formulas`、货币战争 10 表（5 类 × 2 赛季）；`agents`/`hsr_characters` 加时装字段
- **验收**：全量同步 + 条数/字段一致性校验；现有 42 后端 + 47 前端测试不回归

### Phase 4 — UI 三大块
- 导航 2 → 3 块；货币战争两赛季独立切换（互不干涉）
- 新页面：敌人图鉴、卡池历史时间表、伤害公式页、角色详情时装 tab
- 展示字段严格按 Phase 1 schema
- **验收**：E2E 三块全通 + 浏览器视觉终审

### Phase 5 — skill 一条龙 + 仓库副本
- 改造/新建 skill：**检测更新 → 爬取 → 生成报告 → 等确认 → 同步 → 校验 → 汇报**，门禁写死（AD-3）
- HengBerGer 仓库内放副本
- **验收**：一句"更新数据"走完闭环

**顺序**：0 → 1 → 2/3（可并行）→ 4 → 5。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| schema 定错全盘错（Phase 1 是单点） | schema 同时由字段矩阵（主源实测）与种子（nanoka）双侧推导，交叉确认后再动 |
| Cloudflare 盾（Fandom/HHW） | 已放弃依赖；HHW 可用 Wayback 快照兜底（docs/17 §8），后续再议手动过盾 |
| 米游社/GameKee API 变动 | 采集器带状态码/字段断言，失败进报告不静默 |
| 图片版权与稳定性 | 多源备选（AD 待 Phase 1），同步入库不暴露外链 |
| 数据量（种子 19 类 + 爬取增量） | md 进 git 但按类分目录，state.json 记版本避免全量 diff |
