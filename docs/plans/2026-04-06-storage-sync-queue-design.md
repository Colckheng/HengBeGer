# Storage Sync Queue Design

日期：2026-04-06

## 背景

当前项目里，管理端 CRUD、批量替换和 legacy staging 同步最终都会调用 `syncDatabaseToStorage()`，由它负责：

1. 从数据库重新构建快照
2. 写 root storage
3. 刷新 web storage

这条链路目前没有串行保护。在单服务实例内，如果多个写请求几乎同时完成数据库写入，就可能出现多次 storage 刷新并发执行，增加快照互相覆盖的风险。

## 目标

- 在单进程部署下，让 storage 同步按顺序执行
- 保持现有接口和调用方不变
- 尽量缩小改动范围，只包住“快照构建 + storage 写入”这段

## 非目标

- 不处理多实例 / 跨进程分布式锁
- 不把全部数据库写操作改成全局串行
- 不改现有 API 协议和前端调用方式

## 方案比较

### 方案 A：仅为 `syncDatabaseToStorage()` 增加串行队列

推荐方案。

优点：

- 改动最小，所有现有调用点天然受益
- 只影响 storage 刷新，不会把整个管理写链路都锁住
- 和当前单实例部署形态匹配

代价：

- 多个请求仍可能先后完成数据库写入，只是 storage 刷新会排队

### 方案 B：为“写库 + 同步”整条链路加全局 mutex

优点：

- 单实例下一致性更强，语义更直接

代价：

- 所有管理写操作都会被串行化
- 锁持有范围更大，侵入性更高

### 方案 C：文件锁 / 数据库 advisory lock

优点：

- 更容易扩展到多实例

代价：

- 复杂度高，不适合作为当前第一步

## 最终设计

采用方案 A。

在 `src/db/api.js` 中增加一个进程内同步队列，让每次 `syncDatabaseToStorage()` 都通过该队列顺序执行。调用方继续 `await syncDatabaseToStorage()`，不需要改调用协议。

## 数据流

单次同步的执行顺序：

1. 调用方进入 `syncDatabaseToStorage()`
2. 同步任务注册到队列尾部
3. 前一个同步完成后，当前任务开始执行
4. 构建数据库快照
5. 写 root storage
6. 写 web storage
7. 返回本次快照结果

## 失败语义

- 某一次同步失败时，只让当前调用拿到失败
- 队列本身不能因为一次失败而卡死
- 后续同步仍然应该继续执行

实现上，队列尾指针需要在失败时自动恢复到可继续追加的状态。

## 测试策略

至少补一个最小单测，验证：

- 并发触发两次同步时，底层实际执行顺序是串行的
- 前一次任务未完成时，后一次不会提前进入 storage 写入逻辑
- 某个任务失败不会阻断后续任务

## 风险与后续

这一步只能解决单实例内的 storage 并发覆盖问题，不能解决多实例部署下的跨进程同步竞争。若未来服务改为多实例部署，需要把同步锁升级到共享介质。
