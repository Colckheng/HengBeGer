# 19. DB 变更预演——DDL 草稿（T1.5，只评审不执行）

- **状态**：⚠️ 待评审（M1 收尾件；G2 schema v1 已于 2026-10-06 签字）
- **依据**：`docs/18` §3/§4/§7 签字结论
- **约定**：MySQL 8、utf8mb4、Sequelize camelCase 列、`image LONGTEXT`（AD-2）、全部新表走 `ensureSchema.js` 幂等模式在 M3 执行
- **本件不执行任何 SQL**

## 1. 迁移策略（评审点 A）

| 方案 | 说明 | 利弊 |
|---|---|---|
| **A. 新表并存，旧表下线（推荐）** | 新建 `zzz_*` / `hsr_*_v2` 风格新表，从 `data/` md 全量灌入，前端/接口切新表后删旧表 | 不动旧 FK 结构，回滚容易；代价是 M3 有一次前端查询切换 |
| B. 旧表原地改造 | 沿用 `agents/sound_engines/bumbos/drive_disks/hsr_characters/hsr_cones/hsr_relics` 表名，加列 + 废弃 `factionId/roleId/rarityId` 归一化列 | 前端查询零改动；代价是 FK 列改造 + 新旧字段语义混杂期 |

**推荐 A**：旧表列语义（外键 ID 制）与 schema v1（名称+tags 制）根本不同，原地改造必然出现「同名列两义」，与根治 P1-7 表单错位的目标冲突。

## 4. 评审点清单

- **A. 迁移策略**：新表并存（推荐） vs 旧表原地改造
- **B. 主表主键**：`source_id VARCHAR` 唯一键（推荐，源站 ID 稳定） vs 沿用自增业务 ID
- **C. 卡池唯一键**：`(game, source, pool_key)` —— 同池不同源（米游社/bittopup/BWIKI）会各自成行，靠 `source` 隔离；若要跨源合并需去重规则（M3 定）
- **D. `raw_json` 保留源站原始结构**（推荐，diff 与排错用；md_path 是展示真源）
- **E. 货币战争 `season TINYINT`（1/2）**：无跨赛季行，赛季切换=新目录新行

评审通过后：本件随 M1 commit；DDL 执行排期在 M3（`ensureSchema.js` 幂等建表）。
